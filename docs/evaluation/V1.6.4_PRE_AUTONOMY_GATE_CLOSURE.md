# V1.6.4 — Pre-Autonomy Gate Closure

## Overall

V1.6.4 closes the remaining deterministic evidence and post-action verification
boundaries before V1.7. It does not add autonomous resume execution. The
recommended next step is `PROCEED_TO_V1.7`, with the V1.7 implementation itself
still deferred.

## Entity Provenance

Evidence subject resolution now compares structured request arguments with the
subject echoed by a tool payload. If both task or dataset identities exist and
do not match, the observation remains available for audit, but its subject is
unbound and cannot satisfy a target-bound Goal. Static knowledge cannot repair a
missing target-bound operational condition.

Matching, argument-only, and payload-only fallback behavior remain supported.
Identity comparison is exact after whitespace trimming; it is not fuzzy.

## Diagnostic Context

`DIAGNOSTIC_CONTEXT` requires a successful, target-bound diagnostic observation
with at least one meaningful DiagnosisService facts field. `task_name` alone,
`evidence_complete` alone, empty collections, empty mappings, and success
messages do not count. A real partial fact with `evidence_complete=false` does
count as diagnostic context. The Platform Core remains a deterministic facts
plane and does not infer `reason` or `root_cause`.

## Resume Action Verification

The existing `ActionVerifier` remains responsible for the mutation contract:
whether the `resume_task` operation was executed and passed its action checks.
Mutation lifecycle remains represented by Approval status. No new write Tool,
automatic retry, or autonomous execution path was added.

## Resume Goal Verification

`platform_agent.goal_verification.GoalVerifier` is a separate deterministic,
read-only verifier for `resume_task`. It runs only after Action Verification is
`verified` and checks:

- exact post-action task identity;
- task existence;
- availability of post-action execution evidence;
- creation of a new execution rather than reuse of only the old failed run;
- accepted active/success state versus an explicit failed state.

The result is stored in optional `PendingApproval.goal_verification_result`.
Approval `status=executed` continues to describe mutation lifecycle and does not
implicitly mean that the user Goal was satisfied. Therefore these states are
valid and tested independently:

```text
Action Verification = VERIFIED
Goal Verification   = IN_PROGRESS

Action Verification = VERIFIED
Goal Verification   = FAILED
```

Unavailable or wrong-target post-action evidence is inconclusive, never a
success. Old Approval JSON without the optional field remains loadable.

## Smoke Evaluator

The non-formal smoke runner now exposes two machine-readable gates:

- Functional Gate = correctness + safety;
- Strict Gate = Functional Gate + allowed-tool efficiency.

It also supports `--cases` for small selections and `--gate-mode functional|strict`
with strict as the default. Task-planning and write cases now recompute Goal
state from their response contracts rather than hard-coding parity to true.

## Write Safety

The read-only adaptive loop still cannot execute write Tools. HITL,
Precondition, and Action Verification remain in the existing guarded path.
The new GoalVerifier only performs read-only observation. Deterministic tests
record zero direct write and zero adaptive write executions.

## Known Limitations

- Strict smoke remains partial because efficiency is intentionally stricter
  than the functional gate.
- qwen3.7-plus is quota-blocked for the final sanity case.
- qwen-plus formal benchmark remains deferred until the A+ feature freeze.
- Goal Verification confirms deterministic post-action evidence, not the
  eventual long-horizon business outcome. That policy belongs to V1.7 and later.

## Multi-Dataset Resume Goal Verification Follow-up

The first V1.6.4 implementation had one remaining deterministic edge case:
when a resume targeted multiple datasets, a fresh snapshot containing a new
execution for only one dataset could be treated as sufficient because the
state check examined only the non-empty `new_runs` subset.

`GoalVerifier` now derives the expected dataset set from explicit
`arguments.datasets`, or from baseline failed datasets when the argument is
empty. It derives the observed set only from genuinely new post-action runs
and requires:

```text
expected_datasets ⊆ observed_new_datasets
```

before any execution-state check can return `SATISFIED`. The result includes
the deterministic `all_target_datasets_resumed` verification check and records
expected/observed dataset coverage in bounded evidence metadata.

The follow-up regression covers explicit partial coverage, derived partial
coverage, and complete A/B coverage. Result: `32 passed` for the requested
follow-up subset; `compileall` and `git diff --check` also passed. No LLM was
called and the previous qwen-plus/qwen3.7-plus smoke artifacts remain
unchanged.
