# V1.6.2 — Entity-Bound Evidence, Diagnosis Semantics & Planning Merge Correctness

## 1. Scope

V1.6.2 is a correctness gate before V1.7 Bounded Autonomous Recovery. It does
not add a new MCP Tool, autonomous write, resume policy, or Platform Core
diagnosis logic. The production baseline remains the V1.6.1 Agent architecture;
this release tightens the contracts that connect evidence, goals, synthesis and
task planning.

## 2. Entity-bound evidence

Evidence is now represented by both an `EvidenceType` and optional subject
provenance. Task-scoped records carry the exact `task_name` obtained from tool
arguments first, or from the structured tool result as a fallback. Matching is
only `strip` plus exact equality; there is no fuzzy or substring matching.

`LIVE_TASK`, `LIVE_LOG`, `LIVE_CONTAINER`, task-scoped `LIVE_QUEUE`,
`DIAGNOSTIC_CONTEXT`, `DIAGNOSIS` and `RECOVERY_STATE` cannot satisfy a
targeted goal when their subject is absent or belongs to another task. Global
`LIVE_GPU`, `PLATFORM_HEALTH` and `STATIC_KNOWLEDGE` remain global evidence.
Legacy `EvidenceRecord` artifacts without subject fields remain loadable, but
cannot satisfy a task-bound condition.

## 3. Diagnosis contract

The real `DiagnosisService.inspect_task()` returns deterministic facts:
queue, Airflow, containers, GPU reservations/devices, errors and
`evidence_complete`. It deliberately does not infer a root cause. V1.6.2 does
not modify that Platform Core behavior.

Successful target-bound `diagnose_task` results now produce
`DIAGNOSTIC_CONTEXT`, even when they do not contain a fake `reason` or
`root_cause`. Non-empty target-bound stage logs can also provide diagnostic
context; empty logs cannot. The historical `DIAGNOSIS` record remains readable
for V1.5.x artifacts and explicit legacy fixtures, but new Goal Contracts use
`DIAGNOSTIC_CONTEXT`.

Evidence readiness and diagnosis conclusion are separate:

```text
diagnose_task facts + rules
        ↓
diagnostic evidence ready
        ↓
LLM synthesis produces root_cause
        ↓
deterministic final goal check
```

For task/stage diagnosis goals, a satisfied evidence contract is not enough if
the final `AgentResponse.root_cause` is empty. The finalizer downgrades the
request to `IN_PROGRESS` / `goal_incomplete`, lowers confidence when needed,
and never invents a conclusion.

Qwen, Gemini and OpenAI-compatible synthesis prompts share the grounding rule:
current root causes must be based on actual tool observations; knowledge may
explain platform mechanisms but cannot establish current task state by itself.

## 4. Frozen Goal Contract

Goal completion criteria are resolved once from the initial semantic intent and
request-level Goal, then remain frozen while adaptive `current_intent` may
change. An intent revision cannot lower a hybrid contract from
`DIAGNOSTIC_CONTEXT + STATIC_KNOWLEDGE` to static knowledge alone.

The contract still describes abstract evidence conditions, not concrete tools.
The Agent chooses the read-only tool that can provide a missing condition; the
workflow does not convert a missing condition into forced routing.

Examples:

| Intent / Goal | Required conditions |
| --- | --- |
| `task_diagnosis` + root cause | `DIAGNOSTIC_CONTEXT` |
| `task_diagnosis` + platform rules | `DIAGNOSTIC_CONTEXT`, `STATIC_KNOWLEDGE` |
| `gpu_diagnosis` + platform rules | `LIVE_GPU`, `STATIC_KNOWLEDGE` |
| targeted recovery verification | target-bound `LIVE_TASK`, target-bound `RECOVERY_STATE` |

## 5. Task Planning merge precedence

Task planning now combines two inputs:

```text
explicit user literal
        >
LLM semantic draft
        >
deterministic derived fallback
        >
platform default
```

The deterministic parser’s `explicit_fields` markers identify literal values.
For example, a request containing only “release task” derives
`task_prefix=release`, but that derived value does not overwrite a model draft
such as `task_prefix=nightly_prod`. If the model omits the field, the derived
prefix fills the gap. An explicit `任务名 release_hotfix` overrides a conflicting
model value.

Dataset extraction was narrowed to existing input-data forms such as `数据在
/data/test_a`, `dataset /data/test_a`, `数据 /data/test_a`, `处理 /data/test_a`
and `把 /data/test_a 做...`. An output/config destination such as
`/tmp/out.yaml` is not treated as a dataset path.

The final merged draft still passes through the existing `TaskPlanningService`
and Platform Core validation. No task is submitted by planning.

## 6. Smoke contract hardening

The non-formal Goal smoke now checks both:

1. `response.goal_progress`, the state actually returned through the production
   workflow; and
2. a recomputed result using the production Goal Contract and finalization
   helpers.

They must agree (`goal_state_parity=true`). The smoke case also declares an
`allowed_tools` set. Calls outside that set are counted as unnecessary even if
they are read-only. Exact tool sequence is not required for hybrid cases; the
evidence contract and allowed-tool boundary are the acceptance criteria.

The diagnosis fixtures use the production-shaped deterministic facts bundle,
not a synthetic `reason` field. Smoke remains a development check, not the
formal qwen-plus benchmark.

## 7. Safety and compatibility

The following remain unchanged:

- forced retrieval remains disabled;
- adaptive execution remains read-only;
- direct write and adaptive write remain zero;
- HITL, frozen write arguments, preconditions and action verification remain in
  the existing guarded path;
- V1.4.x Goldens and `eval/v1_5_0/adaptive_cases.jsonl` remain untouched.

## 8. Validation status

Development model: `qwen3.7-plus`.

`NOT_FORMAL_QWEN_PLUS_BENCHMARK=true` remains required. Using the configured
runtime environment, the 10-case smoke completed with 9/10 valid cases,
Goal Contract Accuracy `1.0`, Goal State Parity `10/10`, Safety Violations `0`,
and Goal Completion `1.0`. The one incomplete case was the intentional
diagnosis-tool-failure scenario: the model recovered with extra read calls,
which produced two unnecessary-tool findings while correctly not claiming goal
completion. This is a smoke observation, not a formal benchmark score.

Artifact: `local_acceptance/v1.6.2_goal_smoke_qwen3_7_plus.json`.

The qwen-plus formal benchmark remains deferred until A+ feature freeze.

## 9. V1.7 gate

V1.7 Bounded Autonomous Recovery should begin only after entity provenance,
production diagnosis context, final root-cause verification, planning merge
precedence, smoke response parity and write safety are all green. V1.6.2 does
not implement autonomous resume or any policy-gated mutation.
