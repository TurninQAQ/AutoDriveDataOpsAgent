# V1.4.3 — Agent Routing & Tool Semantics

Date: 2026-08-20
Primary Agent Model: `qwen-plus`
Status: `PASS`

## Scope

V1.4.2 established the correct RAG-as-read-only-Tool wiring, but qwen-plus
could still select `get_gpu_pool` for the static question “平台的 GPU
Reservation 是什么？”. The runtime wiring was not forced retrieval; the
remaining issue was a semantic routing contract and lexical collision in the
Tool descriptions.

V1.4.3 keeps the production workflow autonomous and makes the evidence type
explicit: static documentation is searched with `search_knowledge`; current
GPU state is inspected with `get_gpu_pool`; a concrete named task is diagnosed
with `diagnose_task`; task configuration without execution is `task_planning`;
explicit mutation remains governed by the existing write path; greetings use no
Tool.

## Tool semantic contract

`get_gpu_pool` now describes current/live device memory, availability and
active reservations. It explicitly excludes explanations of GPU Reservation
concepts, architecture and rules.

`search_knowledge` describes static documentation and runbooks for definitions,
architecture, mechanisms, policies and operating rules. It explicitly excludes
current runtime state.

The same canonical descriptions are used by the production MCP server and the
dependency-light `FacadeToolClient` catalog.

## Evidence routing taxonomy

All structured Planner providers share one routing contract:

| Evidence class | Intent | Primary evidence |
|---|---|---|
| Static knowledge | `platform_knowledge` | `search_knowledge` |
| Live GPU state | `gpu_diagnosis` | `get_gpu_pool` |
| Live named-task status | `task_status` | `get_task_detail` |
| Named task diagnosis | `task_diagnosis` | `diagnose_task(task_name=...)` |
| Task planning without execution | `task_planning` | no MCP Tool |
| Explicit write/execution | matching write intent | read evidence, then existing HITL path |
| No platform fact | `general_read` | no MCP Tool |

The contract is based on the requested evidence, not a keyword-only rule. For
example, “GPU Reservation 是什么？” is static knowledge while “现在 GPU0 上
有哪些 Reservation？” is live state.

## Evaluation contract

The new independent contract is in `eval/v1_4_3/routing_cases.jsonl` and does
not modify V1.4.1 or V1.4.2. It contains 13 cases covering static knowledge,
live GPU/task state, generic and named diagnosis, hybrid evidence, planning,
explicit write intent and greeting.

The write case distinguishes `submit_task` intent from direct write Tool calls:
the Planner may produce frozen write intent/action data and read-only impact
calls, but the mutation still requires the existing HITL, precondition and
verification chain.

## Safety and invariants

No forced workflow retrieval, second LLM router, prompt/model parameter tuning,
Golden Case change, retrieval change, direct write Tool call, or write safety
boundary change is part of this version.
