# V1.6.1 — Goal Contract & Task Planning Hardening

## 1. Scope

V1.6.1 is a hardening release before V1.7. It does not add a new Tool,
autonomous write capability, or changes to RAG and platform services.

It closes three production-contract gaps found during the V1.6.0 review:

1. Task Planning did not merge deterministic literals from the user request
   back into an incomplete LLM `task_draft`.
2. `EXPLAIN_WITH_PLATFORM_RULES` used a generic live-evidence condition and
   could treat task state plus rules as a complete diagnosis without a root
   cause signal.
3. Runtime Goal progress was not always reflected in
   `AgentGoal.completion_state`.

## 2. Task Planning merge

`TaskPlanningService.plan_from_draft()` now reuses the existing
`HeuristicTaskDraftParser` as an explicit-field parser and merges its result
with the model draft before normal validation:

```text
User literals + LLM semantic draft
             ↓
       field-level merge
             ↓
   TaskPlanningService validation
```

For supported parser fields, an explicit deterministic value wins over a
conflicting model value. This applies to task type/prefix, priority, dataset
paths/names, pipeline literals, timeout, concurrency and existing GPU/image
literal fields. Parser omissions remain unresolved; the merge does not invent
semantic values or defaults outside the existing service defaults.

The regression request:

```text
生成一个 release 任务配置，数据在 /data/test_a，优先级 4，不要执行。
```

recovers `task_prefix=release`, `priority=4`, and
`datasets[0].dataset_path=/data/test_a` even when the fake/model draft omits
those fields. No MCP write Tool is executed.

## 3. Frozen GoalContract

Goal completion now resolves a request-level `GoalContract` once, from the
initial intent and GoalType. The contract contains evidence conditions only;
it never contains Tool names and never routes a Tool.

Examples:

| Initial domain | Goal | Frozen conditions |
| --- | --- | --- |
| `platform_knowledge` | `ANSWER_KNOWLEDGE` | `STATIC_KNOWLEDGE` |
| `task_status` | `REPORT_LIVE_STATE` | `LIVE_TASK` |
| `gpu_diagnosis` | `REPORT_LIVE_STATE` | `LIVE_GPU` |
| `platform_health` | `REPORT_LIVE_STATE` | `PLATFORM_HEALTH` |
| `task_diagnosis` | `DIAGNOSE_ROOT_CAUSE` | `DIAGNOSIS` |
| `task_diagnosis` | `EXPLAIN_WITH_PLATFORM_RULES` | `DIAGNOSIS`, `STATIC_KNOWLEDGE` |
| `gpu_diagnosis` | `EXPLAIN_WITH_PLATFORM_RULES` | `LIVE_GPU`, `STATIC_KNOWLEDGE` |

If adaptive intent changes from `task_diagnosis` to `platform_knowledge`, the
frozen task-diagnosis hybrid contract is not downgraded to static knowledge
only. The model sees missing conditions and chooses an appropriate read-only
Tool itself. There is no `if missing_condition: call_tool()` workflow rule.

The current platform `diagnose_task` service returns aggregated facts and an
`evidence_complete` flag; it does not infer a root cause. `DIAGNOSIS` is only
recorded when an observation contains an explicit structured diagnosis signal
such as the existing fixture/result `reason`, `diagnosis`, or `root_cause`
field. A successful Tool call alone is not sufficient.

## 4. Runtime state synchronization

`goal_progress` is the runtime authoritative state. Final response attachment
copies that state into `AgentGoal.completion_state` using a model copy, so the
following values agree:

```text
response.goal.completion_state == response.goal_progress
```

The same state is used for `SATISFIED`, `IN_PROGRESS`, and `BLOCKED` traces.
Task plan validation and guarded write preparation also update the Goal
Evaluation explicitly: a valid plan means `TASK_PLAN_VALIDATED`; an approved
preparation means `WRITE_PLAN_PREPARED`. Neither means that a mutation has
executed.

## 6. Tests and safety

V1.6.1 adds deterministic tests for draft merge, explicit-priority conflict,
dataset recovery, Goal contract resolution, negative hybrid completion,
contract freezing, and Goal state synchronization in Sequential and LangGraph
runtimes.

MCP, RAG, HITL, Precondition, Action Verification, Frozen Golden files and
direct-write boundaries remain unchanged.

## 7. Status and next step

The qwen-plus formal benchmark remains deferred until feature freeze and quota
availability. V1.7 must not start automatically; it is allowed only after the
V1.6.1 deterministic gates and smoke result remain stable.
