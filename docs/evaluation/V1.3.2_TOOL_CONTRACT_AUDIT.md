# AutoDrive DataOps Agent V1.3.2 Tool Contract Audit

Date: 2026-08-20  
Scope: Phase 1.6 only  
Status: COMPLETE — audit only

This audit does not modify Agent behavior, the Qwen prompt, model parameters,
Golden Cases, thresholds, MCP write boundaries, or evaluation scores.

The audit uses the current production path and the unchanged
`eval/v1_1/agent_tool_cases.jsonl` contract. Its purpose is to distinguish:

- model-selected read evidence;
- optional context used to improve an explanation;
- impact-quality evidence shown in an approval preview; and
- deterministic safety gates that actually protect a write.

## 1. Production Write Path

```text
User Request
    |
    v
Qwen AgentPlan
  - intent
  - frozen write_action
  - optional read-only tool_calls
    |
    v
AgentPolicyEngine.validate_plan
  - read-only allowlist
  - max read calls
  - write intent must have write_action
  - write MCP tools forbidden before HITL
    |
    v
Read-only MCP observations
  - executed only when AgentPlan.tool_calls is non-empty
    |
    v
WriteActionCoordinator.prepare
  - deterministic TaskPlanning/TaskSpec validation for submit
  - get_write_precondition
  - verification baseline for non-submit actions
  - impact preview from selected observations
  - persistent approval record
    |
    v
Human approval / rejection
  - ApprovalStore claim is exactly once
    |
    v
Approved write MCP call
  - precondition attached to frozen arguments
    |
    v
PlatformMutationService
  - validates action arguments/config
  - rechecks the precondition
  - invokes the mutation gateway
    |
    v
Observe again
  - get_action_verification_snapshot
  - retries for eventual consistency
    |
    v
ActionVerifier
  - deterministic action-specific checks
    |
    v
Approval status
  - executed only after verification passes
  - verification_failed otherwise
```

### LLM-controlled steps

The model chooses the AgentPlan intent, frozen `write_action`, and any
read-only `tool_calls`. The model also produces the final natural-language
structured response. The workflow validates these outputs but does not treat
the model's statement of success as execution evidence.

Evidence: `platform_agent/workflow.py:90-129`,
`platform_agent/workflow.py:225-346`, and
`platform_agent/qwen.py:127-171`.

### Deterministic runtime-controlled steps

The policy allowlist, write-intent mapping, TaskSpec validation, precondition
capture/recheck, HITL persistence, mutation gateway call, approval claim, and
post-action verification are deterministic runtime controls.

Evidence:

- Policy and pre-HITL write boundary: `platform_agent/policy.py:50-86` and
  `platform_agent/workflow.py:75-88`.
- Preparation and approval record: `platform_agent/actions.py:92-174`.
- Exactly-once approval claim, mutation result handling and verification gate:
  `platform_agent/actions.py:176-238`.
- Precondition contents and comparison:
  `platform_core/services/precondition_service.py:22-55`.
- Mutation-side revalidation before the gateway:
  `platform_core/services/mutation_service.py:24-107`.
- Deterministic verification contracts:
  `platform_agent/verification.py:38-239` and
  `platform_core/services/verification_service.py:56-166`.

## 2. Deterministic Write Safety Contract

The current safety-critical observations are not the model's
`required_tools` in `agent_tool_cases.jsonl`:

| Runtime gate | Scope | Evidence | Safety role |
|---|---|---|---|
| `validate_task_spec` | `submit_task` | `platform_agent/actions.py:108-120`; `platform_core/services/mutation_service.py:24-49` | Rejects invalid submit config before approval and validates again at mutation boundary. |
| `get_write_precondition` | all writes | `platform_agent/actions.py:128-133`; `platform_core/services/precondition_service.py:22-37` | Captures queue fingerprint, task-config fingerprint, task existence and active task. |
| precondition recheck | all writes | `platform_core/services/precondition_service.py:39-55`; mutation methods at `platform_core/services/mutation_service.py:40-107` | Blocks queue/config/task races after approval. |
| `get_action_verification_snapshot` | non-submit baseline and every post-action verification | `platform_agent/actions.py:135-143`; `platform_agent/verification.py:58-70` | Supplies deterministic state for before/after comparisons. |
| `ActionVerifier` | all supported writes | `platform_agent/verification.py:124-220` | Checks persisted state, queue, DagRuns, containers, GPU reservations and artifacts. |

Therefore, no model-visible read tool in the six Write Cases is
`SAFETY_REQUIRED`. The deterministic coordinator gates are safety-required,
but they are internal write-path controls and should not be represented as
Qwen-selected `required_tools`.

### `get_task_detail` special finding

The suspicion is confirmed for the Write Path: there is no
`_find_observation(observations, "get_task_detail")` and no direct read of that
observation in `WriteActionCoordinator.impact()` or `prepare()`.

The observation can still be serialized into `tool_trace` and passed to the
Qwen synthesis node, so it is not necessarily useless context. It is,
however, not a safety gate, not a precondition source, and not an impact
calculation input. The Write Case requirement is therefore marked
`POSSIBLE_STALE_GOLDEN_EXPECTATION` rather than being treated as model failure
against a safety contract.

### `get_queue_state` special finding

`get_queue_state` affects approval-preview detail only. Missing it does not
prevent `WriteActionCoordinator.prepare()` from creating approval. The queue
race is independently guarded by `PreconditionService.capture()` and
`assert_matches()`, which compare `queue_sha256` and `active_task_name`.

For `delete_task`, the current `impact()` branch does not use the queue values
at all. For stop/resume/priority/submit it improves impact explanation, so the
classification is `IMPACT_QUALITY_REQUIRED`, not `SAFETY_REQUIRED`.

The audit found no read-only case where a tool is required solely to create a
unique historical trajectory. The two clear overstrict expectations are:

1. `get_queue_state` duplicated by `get_task_detail` in the two task-status
   cases; and
2. `get_task_detail` as a hard requirement for the two stuck-diagnosis cases.

The GPU cases retain all three tools because the current contracts divide the
evidence into static task GPU policy, task-scoped runtime diagnosis, and global
GPU contention. This is a functional-completeness judgment, not a request to
force Qwen to emit a particular trace.

## 5. Golden Contract Recommendations

These are recommendations only. `eval/v1_1/agent_tool_cases.jsonl` was not
modified.

### KEEP REQUIRED

- `get_platform_health` for health cases.
- `list_tasks` for catalog listing.
- `get_task_detail` for task-status cases.
- `diagnose_task` for task/stage/GPU diagnosis.
- `get_gpu_pool` for global GPU state and GPU contention cases.
- `get_stage_logs` for OOM/parser-stage failure evidence.
- The no-tool contracts for static knowledge and unsupported restart.
- Outside the Golden Case read-tool list, keep the deterministic internal
  gates: `validate_task_spec` where applicable, `get_write_precondition`,
  mutation-side precondition recheck, and post-action verification.

### MOVE REQUIRED → OPTIONAL

- `get_task_detail` in all six Write Cases: useful context, not a safety or
  coordinator impact input.
- `get_queue_state` in `tool_stop`, `tool_stop_clip`, `tool_resume`,
  `tool_priority` and `tool_submit`: approval impact quality only.
- `get_queue_state` in both task-status cases: duplicate queue context because
  task detail already contains queue status.
- `get_task_detail` in `tool_stuck` and `tool_stuck_clip`: additional static
  context, while `diagnose_task` supplies the operational diagnosis.

### REMOVE AS STALE

No immediate removal is recommended in this audit. The write-case
`get_task_detail` requirement is a candidate for removal if a future contract
decides that optional context must not be scored at all; the conservative
recommendation now is to move it to optional because the observation remains
visible to the synthesis node and response trace.

### ADD REQUIRED

Do not add a new model-visible tool requirement to the current Golden Set.
Instead, keep the following as a separate deterministic Write Runtime
Contract:

- `get_write_precondition` before approval for every supported write;
- `validate_task_spec` before submit approval and again at the mutation
  boundary;
- precondition recheck inside `PlatformMutationService` before the gateway;
- post-action observation and `ActionVerifier` success before marking approval
  `executed`.

## 6. Evaluation Design Recommendation

The current aggregate Tool F1 mixes two different questions. Future reports
should separate them:

### Read Agent Tool Selection

- Read Tool Precision
- Read Tool Recall
- Read Tool F1
- Read Argument Requirement Coverage
- Forbidden Write Tool Rate

These should be calculated on read-only/diagnostic cases and should not treat
optional context as a missing safety control.

### Write Intent Pre-Action Observation Quality

- Write Intent Accuracy: `expected_intent` versus `AgentPlan.intent`.
- Write Action Accuracy: frozen `write_action` versus an explicit action
  contract from the write/task cases or deterministic task-case fixtures.
- Pre-action Observation Recall: only after classifying each observation as
  safety, functional, impact-quality or optional context.
- Forbidden Write Tool Rate: write tools in normal `tool_calls` must remain
  zero.

The current `agent_tool_cases.jsonl` does not carry a complete expected
`write_action` schema, so Write Action Accuracy should use existing deterministic
write/task fixtures until a separately approved schema change exists. No such
schema change was made here.

### Runtime Outcome Gates

Keep these separate from semantic/tool-selection scores:

- Hard Task Success
- Verification Success
- Precondition failure/race protection
- HITL approval state correctness

The production safety boundary is therefore represented by HITL,
precondition, mutation validation and verification—not by whether Qwen happened
to call `get_task_detail` before asking for approval.
