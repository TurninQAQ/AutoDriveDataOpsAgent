# V1.3.2 Ragas Semantic Evaluation Closure

Date: 2026-08-20  
Status: `PARTIAL`

## 1. Scope and evaluation split

This phase closes the observability and validation gap around Ragas semantic
evaluation. It does not replace the production-aligned deterministic retrieval
evaluation.

The formal evaluation split is:

- Retrieval quality: deterministic Context Recall, deterministic Context
  Precision, MRR, and nDCG.
- Generation quality: Ragas Faithfulness, Answer Relevancy, and Answer
  Correctness.
- Ragas Context Precision and Context Recall: secondary LLM-judge diagnostics
  only. They are not the acceptance retrieval metrics.

The existing `eval/v1_1/rag_generation_cases.jsonl` was not modified. The full
dataset contains 12 cases.

## 2. Previous state

The previous Ragas run was `BLOCKED_NOT_VALIDATED` after more than 90 seconds
without identifying the blocking metric. It did not provide enough evidence to
distinguish a provider failure, an embedding failure, a slow metric, or serial
LLM fan-out.

## 3. Root cause

The provider primitives are usable. The observed latency is metric-specific
serial fan-out through Ragas 0.4.3:

| Metric | Observed calls for one case | Resulting behavior |
| --- | --- | --- |
| Faithfulness | 2 serial Judge calls | completed |
| Answer Relevancy | 3 serial Judge calls + 2 Embedding calls | completed |
| Answer Correctness | 3 serial Judge calls + 2 Embedding calls | completed with a finite larger metric budget |
| Context Precision | 5 serial Judge calls, one per retrieved context | slowest diagnostic metric |
| Context Recall | 1 Judge call | completed quickly |

The Qwen Judge calls were the dominant latency source. The compatible Qwen
Embedding calls were sub-second in the single-case traces and returned valid
1024-dimensional vectors. Therefore the previous aggregate delay was not an
Embedding endpoint hang; it was serial Judge fan-out combined with variable
provider response latency. The runner now records each safe API operation,
without storing API keys, Authorization headers, or prompts.

The default metric timeout is finite and evidence-based:

- `PLATFORM_EVAL_REQUEST_TIMEOUT_SEC`: 45 seconds per provider request.
- `PLATFORM_EVAL_METRIC_TIMEOUT_SEC`: 90 seconds per metric.
- concurrency: 1.

The 90-second metric budget provides headroom over the observed one-case
Context Precision latency of about 78 seconds without turning a hang into an
unbounded wait.

## 9. Instrumentation and partial-failure behavior

Each metric row records:

- `case_id`
- `metric_name`
- `started_at`
- `finished_at`
- `latency_sec`
- `status`
- `error_type`
- redacted `error_summary`
- safe API operation count and latency where available

The runner continues after a metric timeout or error. A case can therefore
retain successful scores while marking the failed metric, and aggregate values
only include successful cases for that metric.

## 11. Remaining risks

1. A required full-dataset aggregate using `qwen3.7-flash` is still pending a
   quota reset or a separately authorized Qwen 3.7 Flash quota.
2. Qwen-plus fallback produced partial results because several structured
   outputs hit the provider/framework max-token limit. This should be tracked
   separately from provider latency and not hidden by changing Golden Cases.
3. Ragas semantic metrics remain serial and expensive at concurrency 1. Any
   later concurrency increase requires a separate rate-limit validation.
4. No semantic regression threshold is proposed in this phase; these results
   establish a measured baseline only.
