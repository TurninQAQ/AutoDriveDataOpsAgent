# V1.4.2 RAG Agent Tool Contract Alignment

Date: 2026-08-20<br>
Primary Agent Model: `qwen-plus`<br>
Embedding: `qwen3.7-text-embedding`, 1024 dimensions<br>
Status: `PARTIAL`

## 1. Scope

V1.4.1 formally exposed `search_knowledge(query, top_k)` as a read-only MCP
Tool, but its Planner wording still described the old workflow behavior:

```text
platform_knowledge + tool_calls=[]
→ workflow retrieves RAG context after planning
```

Production V1.4.1 wiring passes `knowledge_retriever=None`. Therefore that
description was inconsistent with the actual runtime and could cause an Agent
to classify a knowledge question correctly while returning no knowledge Tool
call.

V1.4.2 aligns the contract without changing the retrieval algorithm, embedding,
chunking, vector store, Tool Contract baseline, write safety boundary, or model
parameters.

## 2. Runtime contract after alignment

```text
Planner
  ↓
search_knowledge (only when the Agent selects it)
  ↓
MCP ToolObservation
  ↓
deterministic KnowledgeObservation normalization
  ↓
synthesis
  ↓
knowledge_sources + retrieval_trace + tool_trace
```

Production forced retrieval remains disabled. The legacy workflow retriever
parameter remains available for V0.5 compatibility tests and callers that
explicitly provide it; it is not injected by the default runtime.

## 3. Prompt alignment

The Qwen, Gemini and OpenAI-compatible Planner prompts now share the same rules:

- static architecture, mechanism, rule, runbook and recovery questions use
  `intent=platform_knowledge` and call `search_knowledge` when it is present in
  `AVAILABLE_TOOLS`;
- the Planner must not expect workflow-side automatic RAG after planning;
- current task, queue, GPU and platform facts prefer operational tools;
- `search_knowledge` may supplement diagnosis with static rules but cannot
  replace live evidence;
- greeting and ordinary no-fact requests may use no tools;
- write requests continue to produce frozen intent/action data and never put a
  mutation Tool into normal `tool_calls`.

## 4. Knowledge provenance normalization

`platform_agent.workflow.normalize_search_knowledge()` maps successful MCP
rows into the existing `KnowledgeObservation` contract:

```text
rank          → metadata.rank
source/path   → source_path
chunk_id      → chunk_id
title         → title
section       → section
content       → content
score         → score
lexical_score → lexical_score
vector_score  → vector_score
metadata      → metadata
```

The common workflow layer merges legacy retriever observations and Tool-derived
observations by chunk identity. Duplicate chunks are dropped. The original
`search_knowledge` observation is still kept in `tool_trace`; normalized rows
are passed to every Provider's synthesis method and deterministically reflected
in `knowledge_sources` and `retrieval_trace`.

## 5. Knowledge capability flag

`PLATFORM_AGENT_KNOWLEDGE_ENABLED` now has explicit runtime semantics:

| Setting | Runtime behavior |
|---|---|
| `1` (default) | Build KnowledgeService and expose executable `search_knowledge` in the read-only catalog |
| `0` | Do not build the Agent knowledge capability and omit `search_knowledge` from the catalog |

The disabled path does not leave an advertised but unexecutable Tool. Explicit
operator knowledge CLI commands and the historical retriever compatibility seam
remain separate from the default Agent capability path.

## 7. Deterministic regression coverage

The V1.4.2 suite covers:

- static knowledge selects `search_knowledge`, not `get_gpu_pool`;
- Tool results restore knowledge provenance and answer evidence;
- live task status prefers operational tools;
- GPU diagnosis uses live GPU evidence without forced RAG;
- greeting has no Tool call;
- write planning does not use search or write Tools;
- disabled knowledge capability is not advertised;
- MCP server and facade catalog hide unavailable `search_knowledge`;
- V1.4.2 has no optional/forbidden contract overlap.

Legacy V0.5 retriever tests continue to exercise the explicit compatibility
seam. HITL, Precondition, Verification and WriteActionCoordinator behavior was
not changed.

## 11. Final status and remaining risks

`PARTIAL` is the correct status:

- formal Tool wiring, capability gating, provenance normalization and safety
  regressions pass;
- qwen-plus still misselects `get_gpu_pool` for the static knowledge-only
  query;
- no Prompt tuning, model parameter tuning, forced retrieval, Golden Case
  modification, or threshold change was used;
- DeepEval Tool/Argument scores are based on a five-case contract-specific
  sample, not the historical 21-case baseline;
- qwen-plus Agent and any qwen-plus Judge usage should be treated as
  `SELF_MODEL_EVALUATION` when semantic judging is performed.
