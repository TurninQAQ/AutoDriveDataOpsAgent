# V1.5.2 — Resumable Adaptive Baseline

## Scope

V1.5.2 changes evaluation orchestration only. Production Agent routing,
Adaptive semantics, Prompt, Tool Catalog, WriteActionCoordinator, HITL,
Precondition and Verification are frozen.

The V1.5.0 Adaptive Scenario Set remains the only formal source:

```text
Source: eval/v1_5_0/adaptive_cases.jsonl
SHA256: dbd338133139da7785722b0efa1a5718461e62c4df6f888bb133c0ea78199e42
Modified: NO
```

## Why V1.5.1 was insufficient

V1.5.1 passed a 2/2 synthetic Qwen preflight, but the formal collection was
interrupted by a response-header/proxy wait after 3 of 16 cases. The partial
trajectory was preserved, but it could not be reported as a full Adaptive
baseline. V1.5.2 separates Provider Availability from Agent Quality and makes
each Case independently resumable.

## Case state machine

```text
PENDING
  ↓
RUNNING
  ├─ COMPLETE
  ├─ PROVIDER_ERROR
  ├─ AGENT_ERROR / INVALID_RESULT
  └─ INTERRUPTED
```

Each Case receives a fresh fixture client, conversation store and runtime
state. A failed Case attempt is discarded as a trajectory; `--resume` reruns
the Case from its Initial Plan. A COMPLETE Case is skipped unless explicitly
selected with `--rerun-case` or `--rerun-all`.

## Artifacts and atomicity

The V1.5.2 runner is:

```text
scripts/evaluate_adaptive_v152.py
```

It writes:

```text
local_acceptance/v1.5.2_adaptive/
├── manifest.json
├── cases/<case_id>.json
├── failed_attempts/<case_id>.attempt_N.json
├── final_samples.json
└── final_eval.json
```

Manifest, Case and final artifacts use same-directory temporary files,
`fsync`, and `os.replace`. Failure artifacts contain Case/attempt/operation
metadata and sanitized failure classes, not full prompts, credentials or
proxy secrets.

## Resume compatibility

Resume refuses to merge artifacts when any of these change:

- model/provider/endpoint host;
- frozen Case SHA256;
- production base commit;
- request timeout or formal retry attempts;
- Adaptive loop limits;
- canonical Tool Catalog fingerprint.

This prevents trajectories from different runtime contracts from silently
forming one baseline.

## Provider vs Agent failure

Provider failures are recorded as `PROVIDER_ERROR` and do not become Agent
scenario failures. Agent errors and invalid results are recorded separately.
Completed-case metrics are labeled `COMPLETED_CASES_ONLY` when the collection
is incomplete. `FULL_BASELINE=true` is emitted only after all 16 Cases are
COMPLETE.

The formal evaluation uses process-local `--model-retry-attempts` and does not
change production retry defaults. The synthetic preflight remains a start
gate, not a claim that all subsequent Provider operations are healthy.

V1.5.2 also reports actual executed Write tools separately from ordinary
contract-forbidden read tools. A read-only route that violates a Case's
scenario contract is still an Agent-quality failure, but it is not counted as
an executed Write mutation.

## Real qwen-plus baseline

The first invocation passed the synthetic preflight 2/2 and completed 12 of
16 Cases. The remaining four Cases each used two full Case attempts and ended
as `PROVIDER_ERROR` with `provider_auth_error` (HTTP 403). A subsequent
`--resume` invocation ran the synthetic preflight again, but both preflight
requests then returned `provider_auth_error`, so no failed Case was rerun.

No Provider failure is converted into a failed Agent Case, and no
case-specific Prompt example is added after observing a trajectory.

## Known V1.4.4 probes

The Hybrid GPU and Hybrid draining cases in `eval/v1_5_0` remain known
regression probes. They are reported separately from unseen Case metrics. The
V1.5.1 three-Case partial trajectory is historical diagnostic evidence and is
not silently imported into this V1.5.2 baseline.

In the V1.5.2 completed trajectories:

- Hybrid GPU collected both evidence types but in the order
  `search_knowledge → get_gpu_pool`, violating the frozen required order.
- Hybrid draining repeated `search_knowledge` three times, omitted
  `diagnose_task(release_demo)`, and finished with insufficient evidence.
- The no-tool capability case completed with zero tool calls and
  `general_read` intent.

## Decision rule

Only a complete 16/16 collection can decide whether to proceed to V1.6. If
multiple independent Hybrid Cases continue to collect only one Evidence type,
the next step is V1.5.3 Explicit Evidence Sufficiency Contract. V1.5.2 does
not implement that production change.
