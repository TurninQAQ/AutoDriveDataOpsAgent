`EVIDENCE_ROUTING_CONTRACT`. That result demonstrates compliance with the
contract, but is not an independent generalization test. V1.4.4 therefore
adds `eval/v1_4_4/routing_holdout_cases.jsonl` with 48 new queries and a
deterministic guard against exact or substring copying of the production

## Hybrid evidence contract

An explicit request for current state plus a platform rule requires both
evidence sources in the new contract:

```text
Operational MCP Tool + search_knowledge
```

The historical V1.4.3 file is unchanged. No forced retrieval was introduced;
the Holdout only makes the required evidence contract explicit for evaluation.

## Argument Contract

`platform_eval/argument_contract.py` is now the single deterministic matcher
used by the aligned evaluator and the DeepEval adapter.

* `exact` is used for task identities and other exact values.
* `subset` recursively checks a required structure while allowing extra fields.
* `present` checks field presence, including false/zero/null values.
* `non_empty` checks structural presence and a non-empty value.
* `one_of` checks an allowed value list.
* `range` checks numeric lower/upper bounds.

Historical `expected_arguments` remains a recursive subset contract. A new
`argument_contract` overrides the deterministic rule for the same tool while
the legacy expected value remains available as the semantic DeepEval
reference. In particular, `search_knowledge.query` is deterministic
`non_empty`; a rewritten query is not a deterministic false negative. Exact
task identifiers remain strict.

The report retains the legacy key `argument_requirement_coverage` for
consumers and additionally reports:

* Argument Contract Accuracy
* Argument Presence Coverage
* Exact Argument Accuracy

Missing arguments, wrong exact arguments and semantically rewritten search
queries are recorded as different classes.

## Formal evaluation protocol

The frozen protocol is:

```text
V1.4.3 production routing
        ↓
V1.4.4 Holdout freeze
        ↓
one qwen-plus planner collection
        ↓
raw samples saved
        ↓
deterministic metrics
        ↓
DeepEval on saved samples, without recollecting plans
```

The Agent and DeepEval Judge both use `qwen-plus`, so semantic results are
`SELF_MODEL_EVALUATION=true`, not independent third-party evaluation.

### Routing confusions and failures

* `holdout_hybrid_gpu_rule`: expected `get_gpu_pool + search_knowledge`,
  actual `get_gpu_pool`; the explicit rule evidence was missing.
* `holdout_hybrid_demo_draining`: expected `task_diagnosis` with
  `diagnose_task + search_knowledge`, actual `platform_knowledge` with only
  `search_knowledge`; this is a live-task-vs-static lexical routing failure.
* `holdout_no_tool_capability`: expected `general_read` with no tool, actual
  `platform_knowledge` with no tool. Tool safety was preserved, but intent
  labeling was wrong.

The two Hybrid misses are a systematic weakness for explicit combined live
state plus rule requests. No prompt example was added and no rerun was used to
hide it.

### Argument differences

The deterministic failures are structural, not rewritten-query failures:

* `holdout_hybrid_gpu_rule`: missing `search_knowledge.query` because the
  required search tool was not selected.
* `holdout_hybrid_demo_draining`: missing exact `diagnose_task.task_name` and
  the operational tool; the selected search query was non-empty and passed
  its deterministic contract.

No semantically rewritten search query was rejected by the deterministic
`non_empty` matcher. DeepEval's lower ArgumentCorrectness is retained as its
semantic judge result; for example, some default `get_gpu_pool` arguments are
semantically compared even when the deterministic contract imposes no fields.
